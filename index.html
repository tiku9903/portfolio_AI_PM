§ 01 · About

From metallurgy
to machine intelligence.

I started at IIT Ropar studying Metallurgy — a field fundamentally about understanding how materials behave under stress and how systems fail. Turns out that's a great mental model for product thinking.

During my BTech, I got obsessed with a different kind of material: data. I started building ML models, then LangChain pipelines, then full automation systems that could replace entire manual workflows — not just speed them up.

That led me to co-found Three Dots, where we've built 40+ automation systems for clients across real estate, retail, healthcare, and content — saving hundreds of hours of manual work per week, per client.

I don't think about AI as a tool that assists people. I think about it as infrastructure that replaces repetitive work — so humans only touch the decisions that actually require them.

Self-hosted, open-source workflow automation. I use it for complex multi-step pipelines where data privacy matters or where API costs need control. Runs LLM nodes natively.

LangGraph

Framework for stateful, multi-agent reasoning graphs. Used when tasks require memory, conditional branching between agents, or retry logic — like healthcare triage systems.

Make.com

Visual scenario-based automation. Best for client-facing systems where non-technical teams need to understand and modify workflows. Strong API + SaaS connector library.

Core LLM inference layer. GPT-4o for classification + generation tasks; Claude for long-document reasoning and nuanced instructions. Prompt-engineered, not fine-tuned by default.

Zapier

Rapid deployment for SaaS-heavy stacks. Best when the client already lives in tools like HubSpot, Slack, or Gmail and needs fast, no-code trigger-action automation without infrastructure overhead.

Airtable

Relational data backend for automation systems. Acts as the operational database — storing leads, tickets, logs — while connecting cleanly to n8n, Make, and Zapier via API.

My PM Role
  • User research: mapped 4 ticket-handling teams (Customer Support, Warranty, Technical, Returns) and ran a ticket-cost analysis showing 60% of volume came from 5 repeating ticket types — order-status, warranty-eligibility, returns, fitting-help, FAQs.
  • Prioritisation call: chose "trusted classifier + AI-drafted reply with mandatory human edit" over fully autonomous reply. Trust on the trade segment outweighed the marginal volume gain from full autonomy.
  • Stakeholder challenge: negotiated VIP routing for trade customers and a non-negotiable human sign-off on every refund — getting buy-in from operations, legal, and customer service leads before a single line of code shipped.
The Problem

Beacon Lighting's customer support operation had grown into 4 fragmented teams — Customer Support, Warranty, Technical, and Returns — with no shared system and $2.2M in annual labour and overhead costs. With 40,000 tickets/year processed manually, response time averaged 12 hours, and there was zero after-hours capability. The trade division (B2B customers) was highest-value but received no priority treatment. Manual operations meant cost grew proportionally with volume — every new trade contract required new headcount.

The Solution
  • Unified all channels (email, web form, live chat) into a single intake queue
  • NLP engine (BERT + TensorFlow) classifies intent, extracts entities, scores urgency, and runs safety scans on every ticket
  • ML classifier routes to the right agent queue — including instant VIP routing for trade customers
  • 60% of tickets auto-resolved (order status, FAQs, warranty checks via Magento + Customer 360)
  • 30% AI-drafted with human review — agents edit, not write from scratch
  • Escalation keywords trigger immediate safety alerts; humans sign off all refunds
  • 24/7 coverage through always-on automation — no overnight backlog

  • User research: sampled 50+ recorded SDR calls and timed how much was scripted-question repetition vs strategic conversation — found agents spent 60–70% of the call asking the same 4 questions (timeline, budget, pre-approval, intent).
  • Prioritisation call: shipped voice (not chat) first because speed-to-lead in real estate is measured in seconds — voice maps directly to the existing CRM trigger flow, while chat would need new lead-source plumbing.

  • Voice AI agent auto-dials leads within seconds of entering the CRM — from any source (ads, web form, list import)
  • Conversational qualification in natural language — not a robocall or IVR tree
  • Captures timeline, budget range, and pre-approval status during the call
  • Books qualified leads directly onto the agent's calendar; sends SMS confirmation; alerts the human agent
  • Parallel scale — can run hundreds of simultaneous calls with identical script discipline
  • Every call is logged, scored, and reviewable — insight loop for continuous improvement
  • Agents now speak only to leads who have already confirmed readiness to transact

Multi-Agent Healthcare Pipeline (LangGraph)

5-agent conditional graph for full clinical workflow — X-ray triage through nearest pharmacy matching

Built for: Great Learning
My PM Role
  • User research: studied existing clinical-triage workflows to identify where the system loses context between symptom intake, imaging review, prescription, and pharmacy handoff — most failures came from the imaging-to-therapy handoff.
  • Prioritisation call: deliberately scoped V1 to OTC-only therapy with 3-layer safety filters (age, allergy, drug-drug interaction). Refused scope creep into prescription medicines until safety signals were proven on OTC.
  • Stakeholder challenge: defended LangGraph (a conditional graph) over a simpler linear chain to non-technical reviewers by walking through one severe-SpO₂ branching case — showing why linear flow would have routed the patient incorrectly.
Architecture

Built a full agentic pipeline using LangGraph where each agent has a single, well-scoped responsibility. The Ingestion Agent extracts structured patient data. The Imaging Agent classifies chest X-rays (normal / pneumonia / COVID-suspect). Routing logic decides: severe or low SpO₂ → Doctor Escalation Agent; mild → Therapy Agent. The Therapy Agent filters OTC recommendations against age restrictions, allergy conflicts, and drug-drug interactions before suggesting medicines. The Pharmacy Agent geo-matches (haversine formula) the nearest pharmacy with live stock, ETA, and total cost.

Key Engineering Decisions
  • LangGraph conditional graph — not a linear chain — ensures proper branching based on real severity data
  • Safety-first therapy suggestions: 3 safety layers before any medicine recommendation
  • Independent pytest modules for each agent — reliability at agent level, not just system level
  • Streamlit frontend makes the pipeline interactive and auditable by non-technical users
  • Designed for real API integration (live doctor availability, live pharmacy stock) as next milestone
  • Direct precursor architecture for real-world clinical triage automation

§ 08 · How I Think

Product decisions,
not just code.

A product manager's job is to kill 90% of the options. Three AI calls I made where the technically "better" choice was the wrong one — and why shipping is the real skill.
01

The Context

Legal-tech RAG: pure dense retrieval was quietly failing 27% of queries.

Client: US stealth legal SaaS. 180K case documents indexed in a vector DB. Initial build used pure dense embeddings (OpenAI text-embedding-3-large) + cosine similarity — state-of-the-art on paper. Eval showed 89% relevance@5.

Problem: recall metrics were great, but lawyers kept complaining. Why? 27% of real queries were exact-clause lookups ("Section 230 safe harbor") where semantic similarity actively hurt — pulling thematically similar but legally irrelevant cases.

The Tradeoff

Dense retrieval vs hybrid vs graph-RAG.

Three paths:

(a) Fine-tune the embedding model on legal corpus — 4–6 weeks, $$$, ongoing maintenance.

(b) Hybrid BM25 + dense with reciprocal rank fusion — 1 week, proven pattern, small latency hit.

(c) Graph-RAG on entity-linked case law — beautiful research, 3+ months, uncertain ROI.

The Call

"Ship (b) in week 1. Measure. Treat (a) as a backlog item that has to beat hybrid by >8% to justify.

PM reasoning: lawyers don't care about our evals, they care about whether the right clause shows up in the top 3 results. Hybrid retrieval was a known 90% solution that I could ship and measure against the only metric that mattered — the user's 'this is useful' rate."

RAG Hybrid Retrieval BM25 + Dense RRF
Outcome: Relevance@3 jumped from 71% → 94%. Fine-tune shelved. Still in production.
02

The Context

Do we build an MCP server, or stay inside the Zapier/Make happy path?

Mid-2025, a US SaaS client's ops team had 6 internal tools (Airtable, Linear, Notion, Intercom, Stripe, internal admin API). Every time a new workflow came in, we re-built connectors in n8n/Make from scratch. Friction was slowing shipping from 2 days to 2 weeks.

Claude / GPT could theoretically talk to everything via function calling — but every new workflow meant repeating the tool definitions, schemas, and auth boilerplate for the same underlying systems.

The Tradeoff

Build a Model Context Protocol (MCP) server vs keep piling on Zapier.

(a) Build a single MCP server exposing all 6 tools with typed schemas, auth, and audit logs. 2-week upfront cost. Any new LLM app — Claude, Cursor, custom — plugs in once.

(b) Keep using Zapier/Make with per-workflow copies of the same integrations. Zero upfront cost. Ongoing tax: every workflow = 3–5 days of re-plumbing.

The "technically obvious" answer was (a). The PM question was: is it obvious yet?

The Call

"Build the MCP server — but only after workflow №4. Before that, re-use is cheaper than abstraction."

PM reasoning: abstraction has a cost. The first 3 workflows were different enough that a premature MCP server would have hard-coded the wrong shape. By workflow 4, the real interface emerged — and the MCP build took 9 days instead of the estimated 14.

MCP Server Build vs Buy TypeScript Claude Desktop
Outcome: New workflow onboarding dropped 2 weeks → 2 days. Same MCP server now powers 3 internal AI tools.
03

The Context

A support bot was 100% GPT-4o. Unit economics were underwater at scale.

EU stealth B2B SaaS. ~18K support conversations/month, all routed through GPT-4o (then 4.1). Average cost: $0.042/conversation. Customer was willing to pay $0.18/conversation for the tier — but at 90K/month projected volume, GPT-4o costs alone would eat 23% of revenue.

The naive fix: "just use a cheaper model." The real question: cheaper where?

The Tradeoff

Uniform cheaper model vs tiered model routing vs prompt compression.

(a) Move entire pipeline to Haiku / 4o-mini. 6× cheaper. NPS risk: complex tickets get dumb answers.

(b) Router LLM (Haiku) classifies each ticket into {faq, account, technical, escalate}. Simple → 4o-mini. Complex → Sonnet. Escalate → human.

(c) Keep 4o, compress prompts + cache. 30–40% savings but doesn't scale linearly with volume.

The Call

"Ship (b). Route 72% of traffic to the small model. Reserve Sonnet for the 23% that actually needs reasoning."

PM reasoning: the router adds 80ms + $0.0004 per call — but it saves Sonnet inference on the 72% of tickets that are "where is my invoice". Cost/conversation dropped from $0.042 → $0.0091 (4.6× cheaper) with CSAT actually up 3 points (cheaper models handle simple queries faster).

Model Routing Haiku + Sonnet Unit Economics LangGraph
Outcome: $/conversation: $0.042 → $0.0091. Gross margin: 56% → 87%. CSAT +3pts.
